# 洪涝仿真模型前端整体重构计划

> 项目：`risk-emergency-monitor`  
> 文档状态：初版  
> 制定日期：2026-07-14  
> 适用范围：前端架构、地图能力、行政区交互、业务模块、工程化与质量保障

## 1. 重构背景

当前项目是基于 Vue 2、Vue Router、Vuex、Ant Design Vue 和 Webpack 3 构建的洪涝临灾仿真模拟预警系统。系统已经具备短临预报、实况监测、城市内涝、山洪预警、行政区选择、地图展示、时间轴、预警信息、排行与案例收藏等功能，但随着业务持续叠加，核心页面、地图能力和行政区逻辑已经形成较高耦合。

当前主要问题包括：

- 核心业务集中在 `src/views/rapidAnalysis/index.vue`，文件超过 7000 行。
- 四类灾害通过大量条件分支混合在同一个页面中。
- 核心业务状态主要保存在页面 `data` 中，跨组件状态缺少统一管理。
- 地图依赖外部 DiitGIS、DigitalTwin 等封装，并通过 `window.me`、模块变量和 `$refs` 操作。
- 行政区选择、右侧表格钻取、接口查询范围、地图定位范围和预警展示范围混用。
- 请求错误处理、公共参数注入和服务地址管理不统一。
- 存在旧版页面、copy、bak、重复 API 和未确认用途的遗留组件。
- 缺少自动化测试、完整回归用例和持续集成质量门禁。
- 构建工具和基础依赖版本较旧，直接升级风险较大。

本次重构基于独立复制的试验代码进行，可以进行较大范围的架构调整，但仍需保证功能可对照、过程可回滚、结果可验证。

## 2. 重构目标

### 2.1 业务目标

- 保持现有四类灾害核心业务能力不丢失。
- 明确各灾种的数据、图层、时间轴和页面状态边界。
- 解决行政区选择与表格钻取互相覆盖、状态错乱的问题。
- 支持后续新增灾种、指标、图层和展示面板。
- 降低地图外部封装对业务开发的限制。

### 2.2 技术目标

- 将核心页面从 7000 多行降低到约 800～1200 行。
- 所有网络请求进入统一请求层。
- 所有地图操作进入统一 `MapFacade`。
- 自主开发基于 OpenLayers 的 2D 地图封装。
- 分阶段开发基于 Cesium 的 3D 地图封装。
- 建立唯一的行政区状态源和明确的状态流转。
- 按短临、实况、内涝、山洪拆分业务领域。
- 建立可执行的自动化测试和人工回归体系。
- 在业务解耦完成后升级到现代构建工具和 Vue 3。

### 2.3 非目标

- 不自行开发底层 GIS 渲染引擎。
- 不在首轮同时重写 2D、3D、全部业务和框架。
- 不为追求目录整洁而提前删除未确认用途的功能。
- 不在没有行为基线的情况下替换核心业务流程。
- 不要求第一阶段就将全部代码改造成 TypeScript。

## 3. 总体实施原则

1. **先建立安全网，再调整架构。**
2. **先基础设施，后业务模块。**
3. **先 2D 地图，后 3D 地图。**
4. **先 Vue 2 解耦，后 Vue 3 升级。**
5. **新旧地图并行，逐项验证替换。**
6. **行政区浏览、表格钻取和接口查询范围必须分离。**
7. **每个阶段都必须可以构建、运行、验收和回滚。**
8. **所有删除操作必须在引用分析和回归验证后执行。**
9. **避免把存量代码一次性搬迁到新目录而不改变职责。**
10. **优先消除全局状态、隐式依赖和异步竞态。**

## 5. 重构阶段与先后顺序

## 阶段 0：建立项目基线与安全网

### 目标

在不改变业务行为的前提下，明确现有系统的功能边界和验证方式。

### 工作内容

- 确认开发环境和生产构建可以运行。
- 记录 Node、包管理器、浏览器和运行环境要求。
- 建立四灾种核心操作回归清单。
- 记录关键页面和交互截图。
- 梳理现有接口、图层类型、地图工具和外部依赖。
- 记录首屏耗时、构建耗时、产物体积和主要请求数量。
- 建立 ESLint、Prettier 和基础提交检查。
- 标记 `debugger`、调试弹窗和明显无效日志。
- 盘点 copy、bak、旧版页面和疑似死代码，但暂不删除。
- 确认试验副本是否连接真实生产服务，避免对真实数据产生副作用。

### 建议产出

```text
docs/
├── FRONTEND_REFACTOR_PLAN.md
├── REGRESSION_CHECKLIST.md
├── MAP_CAPABILITY_INVENTORY.md
├── API_INVENTORY.md
└── LEGACY_CODE_INVENTORY.md
```

### 验收标准

- 开发启动与生产构建正常。
- 四灾种核心路径都有可重复执行的回归步骤。
- 关键功能都有重构前截图或录屏基线。
- 新增代码不再扩大代码规范问题。
- 已确认当前副本不会误写生产业务数据。

## 阶段 1：统一配置和请求层

### 目标

建立稳定、可测试、可追踪的数据访问入口。

### 工作内容

- 建立唯一 Axios 实例。
- 统一请求超时、业务错误、网络错误和 401 处理。
- 错误请求必须 `reject`，禁止将错误转换为成功 Promise。
- 支持请求取消或使用请求版本号忽略过期响应。
- 集中注入 `systemCode`、`xzqdm` 等公共参数。
- 统一 API 基础地址和 URL 拼接。
- 将服务地址、地图地址和环境差异集中到配置适配层。
- 按领域拆分 API，禁止继续按巨型页面组织接口。
- 为关键接口建立基础契约说明和响应样例。

### 建议结构

```text
src/
├── config/
│   ├── index.js
│   └── runtimeConfig.js
└── services/
    ├── http/
    │   ├── client.js
    │   ├── interceptors.js
    │   └── errors.js
    ├── region/
    ├── forecast/
    ├── rainfall/
    ├── urbanFlood/
    ├── mountainFlood/
    └── case/
```

### 验收标准

- 所有业务请求通过同一个 HTTP 客户端。
- 页面组件不再直接拼接服务地址。
- 网络错误和业务错误能够明确区分。
- 快速切换行政区或时间轴时，旧请求不能覆盖新状态。
- 关键业务接口完成冒烟测试。

## 阶段 2：重构行政区领域模型

### 目标

彻底解决行政区选择、表格钻取、地图定位、接口查询和预警展示互相覆盖的问题。

### 现有问题

当前行政区状态分散在：

- `regionContext.code`
- `positionXzqCode`
- `buttonPostion.locationCode`
- `selected.province/city/county`
- `tableDirllObj`
- `warningCode`
- sessionStorage 中的 `xzqdm`

现有逻辑通过“选择最细行政区”、快照恢复、`regionLock` 和多处同步方法补偿状态冲突，但无法保证同级行政区属于同一父级，也容易受到异步返回顺序影响。

### 新领域模型

```js
{
  browseRegion: {
    code: "370200",
    name: "青岛市",
    level: "city",
    path: [
      { code: "370000", name: "山东省", level: "province" },
      { code: "370200", name: "青岛市", level: "city" }
    ]
  },
  drillStack: [
    {
      code: "370212",
      name: "崂山区",
      level: "county",
      parentCode: "370200",
      source: "ranking-table"
    }
  ],
  currentModule: "urbanFlood"
}
```

### 核心规则

- `browseRegion` 只由用户主动选择和初始化入口修改。
- 点击右侧表格只新增 `drillRegion`，不能覆盖 `browseRegion`。
- `queryRegion`、`mapRegion`、`warningRegion`、`displayRegion` 全部由状态和灾种策略派生。
- 不再用一个行政区编码同时表达浏览、查询、定位和标题。
- 返回操作对 `drillStack` 出栈；退出详情后自然恢复浏览行政区。
- 所有行政区变化只能通过统一 Action 进行。

### 标准 Action

```text
SELECT_REGION
ENTER_TABLE_DRILL
BACK_DRILL
EXIT_DRILL
SWITCH_DISASTER
RESET_REGION
RESTORE_INITIAL_REGION
```

### 灾种策略

```js
const regionPolicies = {
  rainfall: {
    queryLevel: "selected",
    mapLevel: "selected"
  },
  forecast: {
    queryLevel: "selected",
    mapLevel: "selected"
  },
  urbanFlood: {
    queryLevel: "city",
    detailLevel: "county",
    mapLevel: "detail"
  },
  mountainFlood: {
    queryLevel: "city",
    detailLevel: "county",
    mapLevel: "detail"
  }
};
```

例如用户浏览山东省、点击崂山区时，可以同时表达：

- 浏览范围：山东省
- 详情目标：崂山区
- 接口查询：青岛市
- 地图定位：崂山区
- 预警展示：青岛市

### 组件调整

行政区选择组件改造成受控组件，只负责：

- 展示省、市、县层级。
- 加载下一级行政区列表。
- 接收当前选中值。
- 触发 `change(region)`。

行政区组件不再：

- 直接操作地图。
- 决定灾种查询层级。
- 自己维护业务钻取锁。
- 直接修改父页面业务状态。

### 验收标准

- 全国、省、市、县选择和逐级返回正常。
- 表格钻取后退出能够准确恢复原浏览范围。
- 无关行政区的残留编码不能覆盖当前选择。
- 内涝、山洪可以“按市查询、按县定位”。
- 快速连续切换行政区不会发生旧请求覆盖。
- 切换灾种后行政区状态符合各灾种策略。
- 删除 `pickMostSpecificRegionCode` 等补偿式状态选择逻辑。

## 阶段 3：定义统一地图接口

### 目标

业务代码不再依赖具体地图 SDK，为旧地图接入和新地图开发建立稳定边界。

### MapFacade 能力

```text
生命周期
├── init
├── resize
└── destroy

视图
├── setCenter
├── setZoom
├── fitExtent
└── fitRegion

图层
├── addLayer
├── updateLayer
├── removeLayer
├── clearBusinessLayers
├── setLayerVisible
├── setLayerOpacity
└── setLayerOrder

要素与交互
├── addMarker
├── addFeature
├── highlightFeature
├── identify
├── showPopup
├── draw
├── measure
└── clearInteraction

模式
├── switchMode
├── syncView
└── getCurrentMode
```

### 设计要求

- 业务代码不能直接访问 OpenLayers Map 或 Cesium Viewer。
- 图层必须有稳定的业务 ID，不以地图对象引用作为唯一标识。
- 地图事件必须统一订阅和解除，避免重复绑定。
- 每类图层必须具有明确的创建和销毁规则。
- 地图操作应支持请求批次或场景版本，防止过期图层写入。

### 验收标准

- MapFacade 接口能够覆盖现有核心地图操作。
- 业务组件不再新增 `window.me`、`me.earth` 等直接调用。
- 地图生命周期和图层生命周期有明确文档。

## 阶段 4：旧地图适配

### 目标

在不立即替换地图底层的情况下，验证 MapFacade 的接口设计并逐步隔离外部封装。

### 调用关系

```text
业务模块
   ↓
MapFacade
   ↓
LegacyMapAdapter
   ↓
DiitGIS / DigitalTwin
```

### 工作内容

- 使用 `LegacyMapAdapter` 包装现有 2D 地图调用。
- 使用独立适配器包装现有 3D 数字孪生调用。
- 将页面中直接操作地图的逻辑迁移到适配器。
- 将图层缓存从页面中抽离到 `LayerRegistry/LayerCache`。
- 清理 `window.me` 的业务侧读取；迁移期可只在适配器内部兼容。
- 建立地图操作日志，便于新旧实现对比。

### 验收标准

- 原有地图能力通过 MapFacade 可以正常使用。
- 页面和灾种模块不直接依赖外部地图 SDK。
- 时间轴换帧、行政区定位和图层清理行为与基线一致。

## 阶段 5：自主开发 OpenLayers 2D 地图

### 目标

以 OpenLayers 为底层引擎，替换现有 2D 外部地图封装。

### 开发顺序

1. 地图容器、初始化、销毁和 resize。
2. 基础底图和底图切换。
3. 投影注册与坐标转换。
4. 行政区边界、定位和高亮。
5. GeoJSON 等矢量图层。
6. 图片范围图层。
7. XYZ、WMTS、WMS 和 ArcGIS 服务图层。
8. 点位、标注、聚合和弹窗。
9. 点击查询、要素拾取和高亮。
10. 绘制、测距、测面和清除工具。
11. 图层列表、显隐、顺序、透明度和图例。
12. 时间轴图层预加载、缓存和换帧。
13. 图层销毁、事件解绑和内存控制。

### 建议结构

```text
src/map/
├── core/
│   ├── MapFacade.js
│   ├── Map2D.js
│   └── MapLifecycle.js
├── adapters/
│   ├── LegacyMapAdapter.js
│   ├── OpenLayersAdapter.js
│   └── DigitalTwinAdapter.js
├── layers/
│   ├── LayerFactory.js
│   ├── LayerRegistry.js
│   ├── LayerCache.js
│   ├── ImageLayer.js
│   ├── VectorLayer.js
│   └── TileLayer.js
├── interactions/
│   ├── Identify.js
│   ├── Draw.js
│   ├── Measure.js
│   └── RegionDrill.js
└── services/
    ├── ProjectionService.js
    ├── ArcGISService.js
    └── FeatureQueryService.js
```

### 迁移方式

- 保留 `LegacyMapAdapter` 和 `OpenLayersAdapter`。
- 通过开发配置切换新旧地图。
- 按功能逐项迁移，不一次性删除旧地图。
- 对比同一行政区、同一时间、同一图层在新旧地图中的范围和显示结果。

### 重点风险

- EPSG、GCJ-02 等坐标系混用。
- 图片范围和投影不匹配。
- ArcGIS 服务鉴权、代理和跨域。
- 时间轴快速换帧造成闪烁、请求堆积和内存增长。
- 原封装中存在未记录的容错逻辑。
- 同时加载多个大范围图层造成浏览器内存压力。

### 验收标准

- 2D 核心业务不依赖 DiitGIS 封装。
- 行政区定位和业务图层空间位置正确。
- 快速时间轴播放不会出现旧帧覆盖新帧。
- 切换灾种后不存在旧图层和旧事件残留。
- 长时间运行后内存无持续明显增长。

## 阶段 6：统一状态管理

### 目标

将跨组件、跨灾种和跨地图模式的状态从巨型页面迁移到清晰的领域 Store。

### 建议模块

```text
store/modules/
├── region.js
├── disaster.js
├── map.js
├── timeline.js
├── warning.js
└── case.js
```

### 迁移顺序

1. 行政区状态。
2. 当前灾种及模块生命周期。
3. 地图模式和图层状态。
4. 时间轴状态。
5. 预警展示状态。
6. 案例和任务状态。

### 状态边界

应进入 Store：

- 多个组件共享的状态。
- 切换页面或灾种后需要保持的状态。
- 能够由 Action 明确驱动的领域状态。
- 行政区、地图模式、时间轴等关键上下文。

保留在组件内部：

- 弹窗临时显隐。
- 输入框编辑值。
- Hover、展开收起等纯 UI 状态。
- 只被单个组件使用且不需要持久化的状态。

### 验收标准

- `rapidAnalysis/index.vue` 的 `data` 字段减少至少 40%。
- 关键状态只能通过 Action 修改。
- sessionStorage 只保存必要字段，不再保存整个 Store。
- 刷新页面后恢复行为可预测。

## 阶段 7：拆分公共 UI 组件

### 目标

先从巨型页面中剥离无业务副作用的展示区域。

### 建议顺序

1. 灾种导航。
2. 地图工具栏。
3. 图层列表。
4. 图例面板。
5. 预警信息面板。
6. 排行列表。
7. ECharts 统计图表。
8. 时间轴。
9. 案例收藏弹窗。

### 组件约束

- Props 输入、Events 输出。
- 展示组件不能直接请求业务接口。
- 展示组件不能直接访问地图实例。
- 禁止通过多层 `$refs` 调用业务方法。
- ECharts 组件统一管理 init、resize、setOption 和 dispose。
- 组件必须处理卸载时的定时器和事件解绑。

### 验收标准

- 主页面首轮降低到 3000～3500 行以内。
- 子组件职责单一，输入输出清晰。
- UI 拆分前后业务行为和样式基本一致。
- 页面卸载后不存在图表、事件和定时器泄漏。

## 阶段 8：按灾种拆分业务模块

### 目标

将四类灾害拆分成独立领域模块，使主页面成为模块编排器。

### 建议结构

```text
views/rapidAnalysis/
├── index.vue
├── modules/
│   ├── shortTermForecast/
│   │   ├── service.js
│   │   ├── controller.js
│   │   ├── layerBuilder.js
│   │   └── selectors.js
│   ├── liveRainfall/
│   ├── urbanFlood/
│   └── mountainFlood/
├── components/
└── shared/
```

### 推荐迁移顺序

1. 实况监测。
2. 短临预报。
3. 城市内涝。
4. 山洪预警。

先选择相对简单的实况模块验证架构，再处理时间轴和图片图层较多的短临模块，最后处理包含行政区钻取和 2D/3D 联动的内涝、山洪模块。

### 统一模块生命周期

```text
activate(context)
loadData(context)
updateTimeline(frame)
renderLayers(data)
clearLayers()
deactivate()
```

### 设计要求

- 使用语义化灾种常量，禁止继续使用裸数字 `1/2/3/4`。
- 每个模块只清理自己创建的图层、请求和事件。
- 模块切换必须先执行旧模块 `deactivate`，再执行新模块 `activate`。
- 模块不能直接修改其他灾种状态。
- 公共能力进入 `shared`，不能通过复制代码共享。

### 验收标准

- 每个灾种可以独立初始化和销毁。
- 切换灾种无控制台错误、旧请求和旧图层残留。
- 主页面最终控制在约 800～1200 行。
- 新增灾种不需要修改大量既有条件分支。

## 阶段 9：自主开发 Cesium 3D 地图

### 目标

在 2D 地图和业务边界稳定后，逐步替换 DigitalTwin 等 3D 外部封装。

### 前置调研

- 确认水动力数据格式。
- 确认时间帧数量、文件体积和更新方式。
- 确认当前 3D 服务是否使用私有协议。
- 确认模型、地形、影像和淹没数据的坐标系。
- 确认当前 SDK 中无法由公开 Cesium API 直接替代的功能。

### 开发顺序

1. Cesium Viewer 初始化、销毁和 resize。
2. 2D/3D 视角同步。
3. 行政区定位和边界。
4. 点、线、面、模型和影像加载。
5. 洪水淹没范围加载。
6. 水动力时间帧播放。
7. 点击查询、弹窗和高亮。
8. 帧缓存、资源释放和显存控制。
9. 接入 MapFacade 并替换旧 3D 适配器。

### 验收标准

- 2D/3D 切换后行政区和业务时间保持一致。
- 水动力播放结果与旧实现可对照。
- 快速切帧和多次切换不会导致显存持续增长。
- 业务模块不感知 Cesium Viewer。

## 8. 风险与应对

### 业务规则遗漏

风险：现有巨型页面包含大量未文档化的隐性规则。

应对：

- 先建立回归基线。
- 与原项目并排运行。
- 每次只迁移一个业务路径。
- 对关键数据转换增加单元测试。

### 地图结果不一致

风险：原外部封装包含未知的投影、样式和服务兼容逻辑。

应对：

- 保留新旧地图切换。
- 对比同一图层的空间范围、透明度和像素位置。
- 独立记录坐标系和服务类型。
- 先完成 2D，再启动 3D。

### 行政区状态再次复杂化

风险：为了兼容旧代码重新引入多个行政区字段。

应对：

- Store 保持唯一状态源。
- 查询、地图和标题编码只能通过 Selector 派生。
- 禁止组件直接修改行政区状态。
- 为所有状态流转建立单元测试。

### 异步请求覆盖

风险：快速切换行政区、时间轴或灾种时旧请求覆盖新结果。

应对：

- 使用 AbortController、Axios CancelToken 或请求版本号。
- 模块销毁时取消所属请求。
- 图层写入前校验场景版本。

### 重构范围失控

风险：同时修改框架、地图、业务和样式，导致问题难以定位。

应对：

- 严格执行阶段顺序。
- 每个阶段设置明确验收门槛。
- 不把框架升级与业务重写放在同一批次。
- 避免顺手处理不在当前阶段范围内的技术债。

### 外部服务不可控

风险：地图、ArcGIS、天地图和 3D 服务受网络、权限或服务状态影响。

应对：

- 记录服务清单和访问条件。
- 准备最小测试数据或 Mock。
- 区分前端错误与外部服务错误。
- 不将外部服务暂时不可用误判为重构失败。
